# 后端核心引擎与后台任务怎么跑

> 用途：被问「后端启动后有哪些 goroutine 在跑、各自干嘛」时的答案。基准文件：`perpetual-contract/others/backend/metanode.go` + `internal/engine/` + `internal/listener/`。

## 1. metanode.go 启动顺序（装配流水线）

启动是一串线性装配，最后才阻塞在 HTTP（`server.Start()`）：

1. `flag.Parse()` + `conf.MustLoad` 加载 YAML 配置（metanode.go:24-27）。
2. `rest.MustNewServer` 建 server（任意来源跨域），`defer server.Stop()`（:30-31）。
3. `svc.NewServiceContext` 建 ServiceContext（连 Redis、连 Supabase/Postgres 并自动迁移表）（:33）。
4. `chain.NewClient` 建链客户端；失败打印警告、`ctx.Chain=nil`；成功则 `ValidateSepoliaMarkets` + `ValidateOrderSender`（:41-57）。
5. `ctx.Chain != nil` 时启动 `TreasuryDepositWatcher.Start()`（:59-64）。
6. 选指数源：`SpotIndex.Enabled` 走 `CompositeSpotIndex`，否则 `CoinbaseFeed`；都 Start 并赋 `ctx.IndexPrice`（:66-80）。
7. `engine.NewMatchEngine`，赋给 `ctx.MatchEngine` 和 `ctx.OrderBook`（同一实例两个接口）（:83-85）。
8. 注册 HTTP 路由 + ticker WebSocket（:87-88）。
9. `matchEngine.Start(perpAddrs)`（:90-95）。
10. `NewLiquidator(...).Start()`（:98-100）。
11. `NewFundingRateKeeper(...).Start()`（:103-105）。
12. `server.Start()` **阻塞**（:108）。

关键：**所有后台 goroutine 都在 `server.Start()` 之前被 `go` 起来**，主 goroutine 最后才阻塞在 HTTP 上。

| MatchEngine.eventLoop | matchengine.go:103 | 始终 | 事件消费（200ms 轮询 DB）+ 撮合（100ms 兜底） |

## 3. 逐个引擎的 run loop

### 3.1 MatchEngine（见 `05-撮合系统深度拆解.md`，这里只列运行）
- `eventLoop`：事件队列 + poll 200ms + match 100ms。
- `submitLoop`：每 1s 提交 pendingTrades。
- `leaderLoop`：Redis 分布式锁选主（5s 续期）。

### 3.2 FundingRateKeeper（fundingratekeeper.go）

- `settleLoop`：interval = `SettleInterval` 秒，`<=0` 回退 8h。
- `settleFundingRate`（:80-143）每 tick：
  1. `chain==nil` 直接 skip。
  2. 遍历 markets：读链上累计 `GetFundingRate` + `GetMarkPrice` + `indexPrice`。
  3. `fundingDelta = (mark-index)/index/3`，clamp 到 `±MaxRate`（:172-192，约等于 8h=1/3 日）。
  4. 批量 `SubmitFundingRateUpdate`（调 `Dealer.updateFundingRate`）。
  5. 成功后每市场写 `funding_rates` 表。

> 注意：UTC 00/08/16 对齐算法在 `internal/funding/schedule.go`（仅 API 展示用）；keeper 的 settleLoop 是纯 ticker 周期，不对齐 UTC 8 点。

### 3.3 Liquidator（liquidator.go）—— **未实现，面试点**

- `checkSafeOnChain` 恒返回 true（注释掉 `Dealer.isSafe`）（:107-115）。
- `executeLiquidation` 全是 TODO 注释（目标本是 `Perpetual.liquidate`）（:118-156）。
- `checkAllPositions` 里 `traders` 是空硬编码 slice，for 循环体不执行（:67-81）。

**结论：清算器只是骨架，实际每个 tick 无动作、不调链上。**

### 3.4 CoinbaseFeed（coinbasefeed.go）—— 指数价

- WS 连接 `wss://ws-feed.exchange.coinbase.com`，订阅 ticker（product_ids 来自 `Markets[].CoinbaseProduct`）。
- 收 ticker → 写内存 cache + 按 `throttleMs`（500ms）节流 UPSERT `market_quotes` 表。
- 不调链上，实现 `IndexPrice1e6`/`IndexPriceDisplay` 读内存缓存。

### 3.5 TreasuryDepositWatcher（treasurydepositwatcher.go）—— 入金监听

- `loop`：ticker `pollSeconds`（默认 12s），启动时立即 `tickOnce`。
- `tickOnce`：
  1. 拿最新区块 → `safeHead = head - confirmations`（默认 1）。
  2. 读 Redis 游标 `metanode:treasury_deposit:last_block`（失败回退 DB MaxBlockNumber）。
  3. `FilterUsdcTransfersTo(usdc, treasury, fromBlock, safeHead)` 过滤 `Transfer(to=treasury)`。
  4. 每笔去重（tx_hash+log_index）→ 写 `deposits` 表 → `ledger_balances.AddPrimary` 累加。
  5. 全成功才写 Redis 游标；失败不推进，下 tick 重扫。

## 4. ServiceContext 暴露了什么（servicecontext.go:44-79）

| 字段 | 类型/作用 |
|---|---|
| `DB` | go-zero sqlx（接 PG `*sql.DB`）—— position/withdraw/funding_rate 等 |
| `PG` | GORM（DataSource 空时 nil）—— deposit/order/trade/market_quote 等 |
| `Redis` | 缓存（nonce、leader 锁、充值游标） |
| `Chain *chain.Client` | nil=无 RPC；撮合/资金费/充值监听依赖它 |
| `MatchEngine MatchBookSink` | 接口（AddOrder/RemoveOrder），下单/撤单用 |
| `OrderBook OrderBookSource` | 接口（SnapshotOrderBook/MidMarkPrice），深度/行情用 |
| `IndexPrice IndexPriceSource` | 接口（IndexPrice1e6/Display），资金费/行情用 |

**为什么 DB 分两层？** go-zero sqlx 用 `?` 占位符，与 pgx/Postgres 不兼容，所以：sqlx 管一批表（position/withdraw/funding_rate/liquidation/market/kline），GORM 管另一批（deposit/ledger_balance/order/trade/market_quote）。这是面试能体现你懂细节的点。

## 5. 数据落点速查

| 引擎 | 写哪 |
|---|---|
| CoinbaseFeed | `market_quotes`（GORM UPSERT）+ 内存 cache |
| CompositeSpotIndex | `market_quotes`（source=composite）+ `spot_klines` + 内存 |
| TreasuryDepositWatcher | `deposits` + `ledger_balances`；Redis 存游标 |

| MatchEngine | `engine_events`（WAL）、`orders`（状态）、`trades`（成交）；Redis 存 leader 锁 |

## 6. 面试问答预演

**Q：后端启动后到底有几个后台任务？**
A：撮合引擎（eventLoop/submitLoop/leaderLoop）、资金费 keeper、清算器、入金监听器、行情/指数源（CoinbaseFeed 或 CompositeSpotIndex），各自独立 goroutine。

**Q：资金费怎么结算的？**
A：FundingRateKeeper 每 8h 读链上累计费率、标记价、指数价，算 `(mark-index)/index/3` 的增量（clamp 到 MaxRate），批量调 `Dealer.updateFundingRate` 上链，再写 funding_rates 表。

**Q：入金怎么被后端发现的？**
A：TreasuryDepositWatcher 每 12s 扫 USDC 的 `Transfer` 事件（转给 Treasury 地址的），确认区块数后写 deposits/ledger_balances，用 Redis 存扫描游标实现断点续扫。

**Q：清算器是怎么工作的？**
A：（诚实回答）当前是骨架 stub，`checkSafeOnChain` 恒返回 true、`executeLiquidation` 是 TODO，还没真正实现清算——这反而是面试能体现你真看过代码的点。
