# 面试问答预演（高频 + 「为什么这么设计」）

> 用途：考前突击。把最可能被问的问题 + 标准答案 + 加分话术都列在这里。答案都以「我做过这个项目」的口吻写。

## 1. 开场必问

**Q：介绍一下这个项目。**
A：这是一个**去中心化永续合约交易系统**，教学项目。核心模型是「**链下撮合、链上结算**」：用户用 EIP-712 签名订单，relayer（撮合引擎）在内存订单簿里撮合，只有撮合成功的 `trade()` 才上链结算。三个组件——Solidity 合约（资产账本 + 结算 + 资金费 + 清算）、Go 后端（go-zero + GORM，撮合引擎 + 后台任务）、Next.js 前端。

**Q：为什么叫「链下撮合、链上结算」？**
A：高频撮合如果笔笔上链，gas 又贵又慢。所以撮合放在 relayer 的内存订单簿里，只有成交才上链。安全靠两点：① 用户 EIP-712 签名授权订单；② 链上 `approveTrade` 会**重新验签**，所以即使 relayer 不可信，没被本人签过的订单也永远成交不了。

## 2. 架构类

**Q：整体架构是怎样的？**
A：见 `00-总览与链路图.md` 的生命周期图。一句话：登录和下单是链下（签名），撮合是链下内存，成交后 `trade()` 上链，持仓/风险查询直接读链上，资金费和清算是后台任务定时调链上。

**Q：三个角色分别是什么？**
A：用户（trader，签名订单、入金出金）、系统管理员（owner，注册市场/设风参/设撮合引擎）、撮合引擎（relayer/orderSender，撮合并提交成交）。还有 fundingRateKeeper（资金费）、insurance（保险）、liquidator（清算）子角色。

**Q：前端、后端、合约分别怎么交互？**
A：前端→后端走 22 个 REST 接口（下单、查单、查持仓、行情等）；前端→合约只在资金管理时直接上链（approve/deposit/withdraw/建子账户）+ 本地 EIP-712 签名；后端→合约用配置私钥发交易（成交 `Perpetual.trade`、资金费 `updateFundingRate`、各类查询）。

## 3. 合约核心

**Q：仓位是怎么表示的？**
A：用 `paper`（仓位量，正=多、负=空）+ `credit`（资金量）两个字段。实际 credit = `paper × fundingRate + reducedCredit`。比如做多 1 BTC @ $30k = `paper=1, credit=-30000`；做空 = `paper=-1, credit=30000`。多空统一用一套模型和公式。

**Q：只有哪些操作会改变余额？**
A：**只有三种**——资金费率（`updateFundingRate`）、交易（`trade`）、清算（`liquidate`）。这是设计上故意收窄的：所有余额变更都走这三个入口，便于审计和安全。

**Q：`trade` 为什么在 Perpetual 里而不是 Dealer？**
A：`Perpetual.trade` 是入口，它回调 `Dealer.approveTrade`。因为 `msg.sender` 就是调用 trade 的人，合约拿它当 orderSender 并校验在 `validOrderSender` 白名单里——只有撮合引擎能成交。Dealer 统一做验签和结算。

**Q：链上怎么防重放？**
A：靠 `orderFilledPaperAmount[orderHash]` 累计已成交量，成交时校验累计不超过订单总量，所以同一笔签名订单不能被重复吃光。`info` 里的 nonce 字段其实没被合约解析（声明了但没读），这是可以主动提的一个细节。

**Q：强平价怎么算的？**
A：就是「让 `netValue == maintenanceMargin` 的那个价格」。多头分母用 `(1 - liquidationThreshold)`、空头用 `(1 + liquidationThreshold)`。netValue = 余额 + 未实现盈亏，maintenanceMargin = 敞口 × 维持保证金率。详见 `getLiquidationPrice`（Liquidation.sol:221）。

## 4. 撮合引擎（最容易被深挖，见 `05`）

**Q：撮合引擎怎么工作的？**
A：内存订单簿做价格-时间优先撮合。价格用双向链表按优劣排序、时间用同价位 FIFO 队列。所有订单/撮合动作先写 `engine_events` 表（WAL）做重放，撮合结果进 pendingTrades，submitLoop 每 1s 编码成 tradeData 调链上 `Perpetual.trade`，成功才写成交表，失败回滚内存簿。

**Q：多节点怎么保证只有一个在撮合？**
A：Redis 分布式锁 `SetnxEx` 抢锁 + 周期续期，只有 leader 消费事件并撮合；成为 leader 后从 `engine_events` 恢复未成交订单。

**Q：订单进簿的完整路径？**
A：POST /orders → 后端验 EIP-712 签名（`VerifyEOASignature`）→ 写 orders 表 → `AddOrder` 写 `order_accepted` 事件到 WAL → eventLoop 消费事件 → `matchIncomingOrder` 撮合 → 剩余量挂簿。

**Q：成交价怎么定？**
A：取 maker 挂单价（taker 主动吃单接受 maker 报价）。簿内交叉时，更早挂的单当 maker。

**Q：撮合失败怎么处理？**
A：写 `match_rollback` 事件，把 taker/maker 剩余量加回内存簿。链上失败（revert/超时）也走这条回滚。

## 5. 资金费 / 清算 / 入金出金

**Q：资金费怎么结算？**
A：FundingRateKeeper 每 8h 读链上累计费率 + 标记价 + 指数价，算 `(mark-index)/index/3` 增量（clamp 到 MaxRate），批量调 `Dealer.updateFundingRate`，再写 funding_rates 表。

**Q：入金怎么被识别？**
A：两条轨道。Treasury 轨道：用户转 USDC 到国库地址，TreasuryDepositWatcher 每 12s 扫 `Transfer` 事件记 ledger（链下账本）；Dealer 轨道：`approve + deposit` 直接进链上 primaryCredit。`/balance` 会把两者相加。

**Q：出金为什么两步？**
A：`requestWithdraw` 登记 + 时间锁，到期后 `executeWithdraw` 执行。时间锁防止「出金后马上爆仓」跑路。

**Q：清算是怎么做的？**
A：（诚实但加分）合约侧有完整的 `Perpetual.liquidate` → `Dealer.requestLiquidation` 链路，按折扣价清算 + 收保险费。但**后端清算器当前是 stub**，`checkSafeOnChain` 恒返回 true、`executeLiquidation` 是 TODO——还没真正跑起来。

## 6. 「为什么这么设计」合集（背这套逻辑）

| 决策 | 原因 |
|---|---|
| 链下撮合链上结算 | 省 gas、低延迟 |
| EIP-712 签名下单 | 用户授权但不用在线、不用付下单 gas |
| 链上重新验签 | relayer 不可信也无妨 |
| orderId = digest | 天然去重，与合约 filled 对齐 |
| paper + credit 双字段 | 多空统一模型 |
| 手续费进 info 字段 | 链上结算、链下记账 |
| 事件先写 WAL 再进内存簿 | 可重启重放、多节点一致 |
| 出金时间锁 | 防跑路 |
| 子账户 | 隔离风险 |

## 7. 「内行点」——主动提这些能显得你真看过代码

1. **JWT 只签发不校验**：没有 `rest.WithJwt`，业务接口身份来自自报地址参数，是安全缺口。
2. **下单验签可跳过**：`if svcCtx.Chain != nil` 才验签。
3. **清算器是 stub**、**/withdraws 和 /liquidations 是空实现**。
4. **路由真相源矛盾**：`metanode.api` 不含 auth，`routes.go` 被人手加过 5 个端点。
5. **两个后端拷贝**：`perp-backend/` 快照 vs `others/backend/` 完整版。
6. **两个合约都叫 OracleAdaptor**。
7. **手续费后端不算**，链上结算时按 maker/taker 扣。
8. **账户余额结构体叫 `balance`（小写）**，不在 Types.sol。
9. **chain.NewClient 失败 → ctx.Chain=nil**，撮合照跑但成交全 rollback、资金费 skip、充值监听不启动。

## 8. 如果被问到「这个项目有哪些不足/你会怎么改进」

（这是加分题，主动讲不足显诚实）
1. 鉴权不闭环：JWT 未校验、下单验签可跳过 → 应加中间件强制校验。
2. 清算器没实现 → 应补 `checkSafeOnChain` + `executeLiquidation`。
3. 出金/清算接口空实现 → 应实现。
4. 路由手改 `.api` 未同步 → 应收敛到 goctl 流程。
5. 单点 relayer → 多节点选主已做（Redis 锁），但可进一步做签名聚合/抗审查。
