## 2. 发交易的 from/nonce/gas 怎么来（面试高频）

这是链上交易构造的核心，四个要素：

### from —— 不是交易字段，是从私钥推导 + 签名恢复

```go
// NewClient (client.go:74-81)
key, _ := crypto.HexToECDSA(strings.TrimPrefix(cfg.PrivateKey, "0x"))
c.signerKey = key
c.fromAddr = crypto.PubkeyToAddress(key.PublicKey)   // 私钥 → 公钥 → Keccak256 末20字节
```

- `from` 地址 = 配置私钥 `Ethereum.PrivateKey`（YAML）推导出的地址。
- **raw 交易里没有 `from` 字段**，`LegacyTx` 只有 `nonce/gasPrice/gas/to/value/data/v/r/s`。
- 广播后节点用 `v/r/s` 做 Ecrecover 恢复出 from，当作 `msg.sender`。
- 所以 `from` = `c.fromAddr` = 撮合引擎地址，必须等于链上 `validOrderSender`。

### nonce —— 从 fromAddr 查 pending nonce

```go
nonce, _ := c.eth.PendingNonceAt(ctx, c.fromAddr)   // client.go:385
```

### gasPrice —— 查建议价 + 乘倍数

```go
gasPrice, _ := c.eth.SuggestGasPrice(ctx)
// 若 gasMultiplier > 0 且 != 1，则 gasPrice *= gasMultiplier
```

### gasLimit —— EstimateGas（上限 maxGas）

```go
msg := ethereum.CallMsg{From: c.fromAddr, To: &perp, Gas: c.maxGas, GasPrice: gasPrice, Data: data}
gasLimit, _ := c.eth.EstimateGas(ctx, msg)   // 失败回退 maxGas，超过则截断
```

> 注意 `CallMsg.From` 只是给 `EstimateGas` 的模拟调用用，不是广播交易的 from。

## 3. SubmitPerpTrade 完整流程（client.go:376-425）

撮合引擎把成交编码成 tradeData 后调这个方法上链：

```go
func (c *Client) SubmitPerpTrade(ctx, perp, tradeData) (*types.Transaction, error) {
    data, _ := c.perpABI.Pack("trade", tradeData)       // ① ABI 编码 trade(tradeData)
    nonce, _ := c.eth.PendingNonceAt(ctx, c.fromAddr)   // ② nonce
    gasPrice, _ := c.eth.SuggestGasPrice(ctx)           // ③ gasPrice（乘倍数）
    msg := CallMsg{From: c.fromAddr, To: &perp, ...}    // ④ 估 gas
    gasLimit, _ := c.eth.EstimateGas(ctx, msg)
    tx := types.NewTx(&types.LegacyTx{Nonce, GasPrice, Gas, To:&perp, Value:0, Data})
    signer := types.LatestSignerForChainID(c.chainID)   // ⑤ 选签名器
    signed, _ := types.SignTx(tx, signer, c.signerKey)  // ⑥ 私钥签名 → 生成 v/r/s
    c.eth.SendTransaction(ctx, signed)                  // ⑦ eth_sendRawTransaction 广播
}
```

`types.SignTx` 用私钥签名、把结果写进 `v/r/s` —— **从这一刻起 `from` 就隐含在交易里了**（不是填进去的，是签名可恢复的）。

## 4. tradeData 怎么组装（chain/tradedata.go）

`BuildMatchTradeData(taker, maker, amt)`（tradedata.go:167-192）：

1. 校验两单 perp 一致。
2. `OrderFromModel` 把 DB 订单转 `SolidityOrder`，其中 `PackOrderInfo` 把 fee/expiration/nonce 打包成 `info`。
3. 签名归一化 V=27/28（`SignatureForChain`）。
4. `EncodeTradeData(orders, sigs, [amt, amt])` = `abi.encode(Order[], bytes[], uint256[])`，**`orderList[0]` 必须是 taker**。

这个结构正好对应合约 `Dealer.approveTrade` 里的 `abi.decode`（MetaNodeExternal.sol:217）。

## 6. 启动时校验：ValidateOrderSender（client.go:113-126）

启动时（metanode.go）会查链上 `isOrderSenderValid(fromAddr)`，若配置私钥地址不是 `validOrderSender`，直接报错——**否则撮合上链会 revert**。

## 7. chain.NewClient 失败会怎样（面试点）

`NewClient` 失败（RPC 不通/ABI 错/私钥错）→ `ctx.Chain = nil`，影响：

- 撮合：内存撮合照常，但 `submitBatch` 遇到 `chain==nil` 逐笔 rollback，不落链不写 trades。
- 资金费：每 tick 因 `chain==nil` 直接 skip。
- 充值监听：`metanode.go:60` 的 `if ctx.Chain != nil` 导致不启动。
- 链上查询 API：返回空/零（约定）。

无 `PrivateKey` 时 client 只读可用，但发交易类方法（SubmitPerpTrade/SubmitFundingRateUpdate）报错。

## 8. 面试问答预演

**Q：交易的 from 是后端代码里写死的地址吗？**
A：不是。`from` = YAML 配置的 `Ethereum.PrivateKey` 推导出的地址（`crypto.PubkeyToAddress`）。raw 交易里没有 from 字段，节点从 `v/r/s` 恢复出来，等于签名私钥的地址。

**Q：后端凭什么能替用户把成交送上链？**
A：它送的不是「用户签名的转账」，而是「用户签过名的订单 + 撮合结果」。链上 `approveTrade` 会**重新 EIP-712 验签**，确认每笔订单都是本人签的，后端只是提交者（`validOrderSender`）。

**Q：nonce/gas 怎么处理的？**
A：nonce 查 `PendingNonceAt(fromAddr)`；gasPrice 查 `SuggestGasPrice` 再乘 gasMultiplier；gasLimit 用 `EstimateGas` 估算、上限 maxGas；最后 `SignTx` 用私钥签名广播。
